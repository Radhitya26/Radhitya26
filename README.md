## 🧠 About Me

I spend most of my time on Laravel and Go backends, React and Next.js frontends, and the layer between them which is usually where things quietly break. I don't reach for new tools until I need them. Over-engineering leaves scars, and I'd rather the codebase still makes sense six months later to whoever's reading it, including me. 

At some point I built systems that talk to hardware: RFID readers, MQTT brokers, sensors. Physical devices don't respect your error handling, and that experience stuck—I think about failure modes and degradation differently now, even on systems that have nothing to do with hardware.

> *Currently digging into: Advanced Laravel architecture · React performance internals · Distributed system design · Workflow automation patterns*

## 💡 How I Work

| Principle | What it means in practice |
|-----------|--------------------------|
| 🏗️ **Pragmatic Architecture** | Pick tools that solve the actual problem. I've seen microservices used on projects that would've been fine as a single Laravel app. |
| 📈 **Scalability by Design** | Indexing, caching, scaling — these are cheaper to think about at the start than to fix after users show up. |
| 🔍 **Full-Stack Perspective** | What you do on the frontend hits the backend. What you design in the schema shows up in the UI. I keep both in mind. |
| 🛡️ **Production Readiness** | If the system can't handle a failed queue job or a database timeout, it's not done yet. That's just what "done" means to me. |
| ⚙️ **Automation & Integration** | I don't repeat manual work. n8n, webhooks, workflows — these are how you build systems that scale without scaling the team. |
| ✍️ **Code for Humans** | I'd rather have a codebase a junior can read than one only I can maintain. Tests are how I know the thing actually works. |
